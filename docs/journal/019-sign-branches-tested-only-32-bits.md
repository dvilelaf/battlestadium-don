# 019 · The 3D view rolled by 90 degrees: bltz and its siblings tested only 32 bits

- **Date:** 2026-10-13
- **Task:** T-202
- **Status:** resolved in the recompiler (patch 0039, not yet in `series`); not run in the game (no game build was allowed in this task)

## Symptom
In the practice match the 3D view flickers between upright and rolled by exactly 90 degrees (the fighters
lie horizontally, Naruto and Sasuke are separated vertically) while the HUD stays upright. Command:
`DON_VU1=microvu build/linux-3d/don --headless --renderer software --shots ... --input-script <route> disc/SLPS_256.75`.
The route is reproducible (two runs, 161 shots, byte-identical). The roll is not two long stretches but a
per-blank flicker, in clusters: it starts near blank 6685, is dense at 6717-6790 and returns around
7060-7085, 7170-7205 and 7235-7300.

## Classification
Wrong code generated by the recompiler (an instruction translated with the wrong width). Same family as
journal 013 (PEXEW), but in a branch, not a macro.

## Investigation
1. Console comparison: PCSX2 on a virtual display, 137 grabs (idle and key mashing, about 70 s of fight).
   The camera follows the fighters, tilts a few degrees when one is knocked away, shows cut-ins, and is
   never rolled by 90 degrees (0 of 137).
2. RAM dumps of 50 consecutive handler ticks (6700-6749). A RenderWare frame near guest 0xd9b900 holds two
   identical matrices (modelling 0xd9b910, LTM 0xd9b950). Over those ticks it flips 25 times between two states
   that match the upright and rolled shots (handler tick T = presented blank T+11). The rolled matrix is
   exactly the one built with the up hint (1,0,0) instead of (0,1,0).
3. A gdb watchpoint on the matrix: the writer is the camera look-at, FUN_0013a850 (0x13a850): at = target - eye,
   normalised, then `d = 1.0 - |at.y|` in the game's soft-float doubles and `d < 0.0001` (constant
   0x3f1a36e2eb1c432d). When true it takes the "looking straight up/down" branch with the hint on the x axis.
4. gdb on the soft-float subtract FUN_00130830(1.0, |at.y|): in some ticks it returns garbage. Failing:
   3f49aecbc0000000 gives c01c00cd765e0000; 3f471f1ac0000000 gives c01c00b8f8d60000; 3f42bd4ae0000000
   gives c01c0095ea570000. Correct: 3f4c86b000000000 gives 3feff8de54000000 (about 0.9992). The compare then
   sees a negative number, so it is "less than 0.0001".
5. FUN_00130598 (gcc fp-bit add/sub of the unpacked parts, 0x130598), called from 0x13087c. Unpacked
   a = 1.0: class 3, exp 0, fraction hi 0x10000000, lo 0. b: exp -11, fraction hi 0x19aecbc0 (failing) or
   0x1c86b000 (passing). In the failing case the result is sign 1, exp 1, fraction 0x78019aec_bc000000.
6. The generated code at 0x13070c: `dsubu v0,t2,t3` then `bltz v0`, emitted as `GPR_S32(ctx, 2) < 0`. t2 - t3 is
   positive as a 64-bit value (0x0fff...), but its low word has bit 31 set (here ...bc000000), so the port took
   the "negative" path and wrote sign 1 with the negated fraction. Passing cases happen to have bit 31 clear.

## Cause
`ControlFlowEmitter::conditionalBranchExpression` (`ps2xRecomp/src/lib/control_flow_emitter.cpp`) emitted
`GPR_S32(ctx, rs)` for blez, bgtz, bltz, bgez and their likely/link forms. These MIPS instructions compare the
whole 64-bit register with zero. The faulty instruction in the game is the `bltz` at 0x13070c. The generated
code has 7538 such sites (2976 `<`, 2144 `<=`, 858 `>`, 1560 `>=`); any of them with a 64-bit operand whose
low word differs in sign from the whole is wrong.

## Fix
Patch `patches/ps2recomp/0039-sign-branches-test-64-bits.patch` (4 lines): `GPR_S64` in the four expressions.
The generated code must be regenerated (`tools/pipeline/generate.sh`) and the game rebuilt. Not added to `series`.

Sibling instructions checked against the translators (and PCSX2 `R5900OpcodeImpl.cpp` semantics):

| Instruction | Width in the translator | Result |
|---|---|---|
| bltz, bgez, blez, bgtz and l/al forms | 32 bits (bug) | fixed by 0039 |
| beq, bne, beql, bnel | `GPR_U64` | correct |
| slt, sltu, slti, sltiu | `GPR_S64` / `GPR_U64`, immediate sign-extended to 64 | correct |
| movz, movn | `GPR_U64` test, whole 128-bit register moved | correct |
| dsubu, daddu, dsll/dsrl/dsra (+32, v) | 64-bit | correct |
| teq, tne, tge, tlt (+u) | 64-bit | correct |
| and, or, xor, nor, andi, ori, xori | `GPR_U64` | correct |

(Read from the translator source, not tested one by one against edge operands.)

## Verification
- `tests/runtime/test_branch_sign.py` (builds a tiny MIPS ELF, runs the recompiler, reads the emitted
  conditions), run with pytest through uv:
  with the unpatched recompiler: `1 failed` (`GPR_S32(ctx, 4) < 0` instead of `GPR_S64(ctx, 4) < 0`);
  with the recompiler relinked with the patched emitter (`DON_RECOMP=work/roll/recomp-fix/ps2_recomp`):
  `1 passed`.
- The patch reverses cleanly on the scratch worktree (base series + 0037 + 0038) that carries the change.
- NOT done: regenerating `generated/`, rebuilding and running the game. The fix has not been seen in the game.
- Expected picture after a rebuild: no 90-degree flips at blanks like 6685, 6717-6790, 7060-7085 and the later
  stretches; the camera stays upright as on the console. Re-run the same route and the roll detector
  (`work/roll/classify.py`, gradient ratio >= 0.85 means rolled): expect zero rolled shots.
- Other behaviours may change in the whole game (any soft-float or 64-bit code) and need a regression run.

## Follow-up (2026-10-13, T-202/T-207 integration, journal 020): the fix in the game

Patch 0039 is in the series; the recompiler was rebuilt, `generate.sh` rewrote 4,786 generated files (audit
clean, 0 files left with a `GPR_S32 ... < 0` sign test, 7,538 `GPR_S64` ones), `build/linux-dev` was rebuilt
(7 min 8 s, 6.4 GiB peak). On the route to the match (`DON_VU1=microvu`, no sound, shots every 5 blanks over
6600-7400, `work/shots/int-roll0039/`) `work/roll/classify.py` flags one shot of 161 (blank 6600, the "FIGHT"
banner, which scored the same before the fix) against 32 of 161 before; twelve shots looked at, including
blanks 6685, 6720, 6745, 7070, 7180, 7260 and 7290 that were rolled, are upright. The state line of blank 60
(journal 017's check) is identical in the four `DON_TRACE_STATE` values: `ramHash=b752953ed2040cc3`.
